Section 01

Abstract

Questigo is a game-based interactive learning platform that teaches Computer Science concepts through active construction rather than passive reading or multiple-choice testing.

Traditional e-learning tools rely heavily on video lectures and quiz-style assessment. These test recognition — a student picks the right option from a list — but they rarely test whether a learner truly understands how the parts of a system fit together. Questigo addresses this gap with a distinctive gameplay model: instead of answering a question, the student reconstructs a real process — for example, the SQL query execution pipeline (FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY) — by assembling shuffled concept tiles into the correct order. Every connection is validated individually, and wrong links are turned into targeted teaching moments.

The platform wraps this mechanic in an RPG-inspired progression system: students earn XP, climb through a fixed 10-level ladder, unlock achievements, and compete on a leaderboard. Content is organised as a Skill Tree in which each node unlocks only after its prerequisite is completed. A second mechanic — a Monaco-based Coding Challenge that runs and grades real Python against hidden test cases — demonstrates that the architecture generalises beyond a single game type.

A defining feature is the AI-assisted content pipeline: a teacher uploads a PDF of study material, a Large Language Model (via the Groq API) converts it into structured, playable quests, and the teacher reviews and approves the generated answer key before any student sees it. This human-in-the-loop design keeps AI-generated content trustworthy — a critical requirement for an educational tool.

The system is built as a modern full-stack web application: a React 19 + TypeScript single-page frontend and a Python FastAPI + PostgreSQL backend, secured with JWT authentication. The complete MVP — authentication, both game mechanics, XP/level persistence, achievements, leaderboard, student profile, teacher authoring and the full AI generation-and-approval workflow — is implemented end-to-end and is fully database-driven with no mock data.

Section 02

Introduction & Motivation — Why This Project

Learning to program is difficult, and a large part of that difficulty is engagement. Most learners begin with enthusiasm and abandon the effort long before competence sets in. The reason is rarely the material itself — it is the delivery. Slides, PDFs, and multiple-choice quizzes are passive; they do not require the learner to do anything with the knowledge, and they provide little of the moment-to-moment feedback and reward that sustains motivation.

2.1 Why I Chose This Project

I chose to build Questigo for four reasons that together make it a strong MCA major project:

  • It solves a real, relatable problem. Every student in the panel has struggled to stay motivated while learning a technical subject. The problem needs no explanation.
  • It is technically substantial. The project spans a full modern stack — a reactive SPA, a typed REST API, a relational database, JWT security, a sandboxed code runner, and a live LLM integration — demonstrating breadth across the MCA curriculum (web technologies, DBMS, software engineering, and AI).
  • It is genuinely novel. The "reconstruct-the-pipeline" mechanic is not a re-skinned quiz; it is a different kind of assessment that tests structural understanding. This gives the project a clear, defensible point of originality.
  • It is buildable and demonstrable. Unlike vague "AI tutor" ideas, every feature here produces a visible, clickable screen, which makes for a compelling live demo.

2.2 The Core Insight

A quiz tests recognition. Questigo tests construction. Recognising the definition of normalization is easy; correctly ordering the steps to take a table from an unnormalized form to 3NF proves you actually understand the process. Computer Science is full of such processes, lifecycles, and pipelines — SQL execution, normalization, the OSI model, the software development lifecycle, the OS process lifecycle — and every one of them maps naturally onto the Sequence Builder mechanic.

2.3 Naming

The name Questigo fuses Quest (the RPG unit of progress that frames each learning activity) with a suffix suggesting go / ignite — capturing the product's intent: to turn the grind of learning into a sequence of achievable, rewarding quests.

Students struggle to learn programming and CS fundamentals effectively because current tools share a common set of weaknesses:

  • Learning is passive and theory-heavy — watch, read, memorise.

5.4 Design Principles

  • Simplicity first — the obvious implementation over premature abstraction.
  • One responsibility per file — components render, services compute, CRUD persists.
  • Server is the source of truth — XP, level, and completion are re-verified server-side; the client cannot spoof rewards.
  • Standard response envelope — every API response is { data, error }, so the frontend handles success and failure uniformly.

Section 08

Implementation — Modules & Features

The system was built in six phases; the following modules make up the delivered platform.

8.1 Authentication & Authorisation

Registration and login issue a signed JWT ({ sub, role, iat, exp }) with bcrypt-hashed passwords. The token is attached to every request by an axios interceptor; a 401 automatically logs the user out. On the frontend, <ProtectedRoute role="STUDENT"> redirects unauthorised users, and backend require_role dependencies guard every teacher/student endpoint.

8.2 Student Experience

  • Dashboard — welcome banner, XP progress bar, level badge, live per-track completion cards, and real achievement counts.
  • Skill Tree — the subject rendered as an unlockable node map (completed / available / locked states); coding nodes carry a distinct badge.
  • Sequence Builder — the flagship mechanic (detailed in §9).
  • Coding Challenge — a Monaco editor where the student implements solution(...), runs it against test cases, and earns XP only when all pass.
  • Profile — level, XP, completed-quest history, and an achievements grid (unlocked vs. locked).
  • Leaderboard — all students ranked by XP, with the current user highlighted.

8.3 Teacher Experience

  • Dashboard — real subject/quest/student counts pulled from GET /teacher/overview.
  • Generate — upload a PDF or paste text, choose quest type (Sequence / Coding) and count, and produce AI drafts.
  • Approve — review each draft (correct sequence, distractors, per-link explanations, or the coding prompt + tests), then approve or reject. Nothing reaches students until approved.
  • Author & Edit — hand-build quests from scratch and structurally edit them (add / remove / reorder steps, manage distractors, edit all fields) for both quest types.
  • Students — a ranked roster with each student's completion and achievement counts.

8.4 Gamification Engine

XP & Levels

Additive XP, never decreasing; a +30 Clean Build bonus for flawless solves. Level recomputed server-side after each award.

Achievements

A 7-achievement catalogue (First Quest, Clean Architect, Boss Slayer, Trifecta, Rising Star, Perfectionist, Veteran) with per-user unlocks and stacked toasts.

Skill-Tree Unlocking

A node is playable only when its predecessor is completed — enforced from persisted quest_attempts.

Leaderboard

Direct XP-descending ranking of all students, refreshed on load.

8.5 AI Content Pipeline

The signature module. A teacher's PDF is parsed (pypdf), sent to the LLM with a strict JSON-mode prompt, and the response is normalised into quest drafts (tiles, correct order, distractors, per-link explanations — or a coding prompt with reference-computed test cases). Drafts land as PENDING_TEACHER_REVIEW; only teacher approval publishes them. A single OpenAI-compatible client targets Groq by default, with an offline deterministic stub so the demo works even with no API key.

Section 09

Coding — Core Algorithms & Logic

Four pieces of logic are the technical heart of the project. Each is shown below in representative form.

9.1 Per-Link Sequence Validation

The Sequence Builder does not grade the whole answer at once — it validates each connection between adjacent tiles. A link is correct only when both endpoints hold the tile the canonical order expects. Wrong links surface the teaching explanation for the connection that should be there.

// The canonical answer is simply the order of `tiles`.
function validatePipeline(placed, correctOrder, linkExplanations) {
  const links = [];
  for (let i = 0; i < placed.length - 1; i++) {
    const fromOk = placed[i]?.id     === correctOrder[i].id;
    const toOk   = placed[i + 1]?.id === correctOrder[i + 1].id;
    const ok = fromOk && toOk;
    links.push({
      ok,
      // turn a wrong link into a teaching moment
      hint: ok ? null
               : linkExplanations[`${correctOrder[i].id}->${correctOrder[i+1].id}`],
    });
  }
  const solved = links.every(l => l.ok) &&
                 placed.length === correctOrder.length;
  return { links, solved };
}

9.2 XP Award & Level Derivation (server-side, anti-spoof)

Completion is re-verified on the server. XP is awarded only on the first completion; the level is derived from total XP so it can never disagree with it.

def level_for_xp(xp: int) -> int:
    # fixed threshold table — Level 1 = 0 XP ... Level 10 = 8000 XP
    level = 1
    for lvl, threshold in LEVEL_THRESHOLDS:
        if xp >= threshold:
            level = lvl
    return level

def complete_quest(db, user, quest, clean_build):
    attempt = get_attempt(db, user.id, quest.id)
    if attempt and attempt.status == "COMPLETED":
        return {"xpAwarded": 0, "alreadyCompleted": True}   # idempotent

    reward = quest.xp_reward + (30 if clean_build else 0)
    user.xp += reward                          # additive, never decreases
    user.level = level_for_xp(user.xp)         # recomputed, never drifts
    mark_completed(db, user.id, quest.id, clean_build)
    unlocked = check_and_unlock(db, user)      # achievement predicates
    db.commit()
    return {"xpAwarded": reward, "leveledUp": ...,
            "unlockedAchievements": unlocked}

9.3 Sandboxed Python Code Runner

Coding submissions run in an isolated (python -I) subprocess with a 5-second wall-clock timeout. Each test calls the student's solution(...) and compares string output; compile errors, exceptions, and timeouts all surface as failed tests. Crucially, the client-reported result is never trusted — the server re-runs the code before awarding XP.

def run_tests(source: str, test_cases: list) -> list:
    results = []
    for tc in test_cases:
        harness = source + f"\nprint(solution({tc['input']}))"
        proc = subprocess.run(
            [sys.executable, "-I", "-c", harness],   # isolated interpreter
            capture_output=True, text=True, timeout=5,  # wall-clock limit
        )
        got = proc.stdout.strip()
        results.append({
            "id": tc["id"],
            "passed": got == str(tc["expectedOutput"]).strip(),
            "description": tc["description"],   # inputs/expected stay server-side
        })
    return results

9.4 AI Generation with Self-Consistent Test Cases

For coding quests, the LLM is also asked for a referenceSolution. The server runs that reference through the same code runner to compute each expected output — guaranteeing the generated tests are actually solvable — then discards the reference. This closes the classic risk of an AI inventing a test whose "expected" answer is wrong.

def expected_from_reference(reference: str, inputs: list) -> list:
    # run the model's own reference solution to derive ground truth
    computed = []
    for inp in inputs:
        out = run_single(reference, inp)          # same sandbox as students
        computed.append(out if out.ok else model_fallback(inp))
    return computed   # reference is never stored or shown to anyone

Section 13

Future Scope

The architecture was deliberately built to extend. Each item below is a natural next step, not a rewrite.

Hardened Code Sandbox

Replace the subprocess runner with a container-isolated judge (Judge0 / gVisor) for safe, multi-language execution at scale.

More Node Types

A free-form Transition Graph builder and rapid Concept Strike recall rounds — both slot into the existing Skill-Tree engine.

Adaptive Difficulty

Use a student's attempt history to tune quest difficulty and recommend the next node — a personalised learning path.

Multiplayer Battles

Real-time head-to-head sequence or coding races over WebSockets, with a live spectator leaderboard.

Mixed-Kind AI Generation

Section 14

Conclusion

Questigo set out to answer a simple question: what if learning a technical subject felt less like reading a textbook and more like playing through a well-designed game? The delivered platform answers it concretely. Students learn by reconstructing real systems — validated connection by connection — and by writing and running real code, all inside an RPG progression of XP, levels, achievements, and leaderboards that keeps them coming back.

Technically, the project is a complete, modern full-stack application: a typed React 19 SPA over a layered FastAPI + PostgreSQL backend, secured with JWT, and integrated with a live LLM to turn a teacher's PDF into playable content — always behind a mandatory human-approval gate that keeps the AI trustworthy. Every MVP objective was met, and several post-MVP features were delivered on top. Crucially, the system is fully database-driven with no mock data, which means the demo shows the real product, not a facade.

As an MCA major project, Questigo demonstrates competence across the full breadth of the discipline — web technologies, database design, software architecture, security, and applied AI — while contributing a genuinely original idea: assessment by construction rather than recognition. It is ambitious in concept, complete in execution, and honest about its limits and its road ahead.

In one line: Questigo turns passive, quiz-based learning into an active, game-based journey where students build their understanding — literally — one validated connection at a time.
